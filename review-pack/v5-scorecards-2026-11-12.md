## 四、审稿人界面实拍：这些分是怎么一项项填进去的

截图来自本地真实前后端（不是静态稿）：

- `visual-check/review-ui/academic-94-filled.png`：学术赛道，5/5 维完整，当前合计 74.4 / Q2 二区。
- `visual-check/review-ui/absurd-225-filled.png`：荒诞赛道，5/5 维完整，当前合计 79.7 / Q2 二区。

两张图里可以看到每个维度的四件事同时存在：

1. 分数输入框（0–100）；
2. “为什么给这个分”理由框；
3. “正文证据（必填）”框；
4. 当前分数锚点 + 本维度完成状态 + 底部实时合计/封顶提示。

**不是只截了界面。** 我用同一份 v5 数据实际提交过一次审稿报告：

- `POST /api/review/assignments/2/submit` 返回 **201**；
- 报告 `scores` 中五个维度都写入了 `score / reason / evidence / label / points`；
- 数据库 `review_reports.scores` 可直接读到同样的五维证据；
- 该任务状态变为 `completed`，报告 id 为 1。

这说明“逐维填、逐维证、服务端校验、落库”是通的，不是只做了个表单外观。

## 五、这次到底改掉了什么“随手高分”

| 旧问题 | v5.0 的处理 |
|---|---|
| 默认 70 分、平均分堆在 80 附近 | 去掉默认分；每个维度必须审稿人主动给分，空着不能提交 |
| 只写“不错/建议修改” | 每维必须写理由（≥4 字）+ 正文证据（≥8 字） |
| 理由为空时用建议分兜底 | 兜底逻辑已移除；缺理由直接拒绝 |
| 七维自由结构、不同稿用不同维度 | 固定双赛道五维；学术/荒诞各一套 key，提交时校验覆盖 |
| 先加总再“看着给个等级” | 权重合成 → 硬门槛封顶 → 分区，等级由分数出来，不能手工抬 |
| 所有稿都 80+ | 本次实测分布：56–92 的单维、64.0–86.7 的总分；Q1/Q2/Q3 都有 |

## 六、诚实说明

- 这份报告基于当前工作区的 v5.0 代码与四篇样稿正文；分数是逐维人工判断，不是模型批量打分。
- 审稿界面截图来自本地演示后端与本地前端 dev，**不等于线上已发布**。线上目前仍是旧口径，v5 前端/后端还需要 build + deploy 才会对真实审稿人生效。
- 四篇里没有 90+，是因为 90 的口径是“顶刊级”，不是“这篇不错”。如果要把某篇抬到 90，必须先把对应维度的证据补到可核查，而不是改总分。
